# Wedding Venue Agent

An AI agent that transforms a real, recurring workflow: my brother evaluating
destination wedding venues and reaching out to them. It searches candidate
venues, reads each page, extracts a normalized record, scores it against the
couple's must-haves, and drafts a personalized inquiry email — **drafting, never
sending**, and **escalating to a human** anything it can't confirm.

Built as an FDE case study around the loop:
**Audit → Build → Evals → Deploy → Observe → Improve.** See `FRAMEWORK.md` for
the point-by-point mapping.

## Run it (no API keys needed)

```bash
pip install -r requirements.txt
python main.py --criteria criteria.json      # runs offline in MOCK mode on fixtures
python -m evals.run_evals                     # runs the eval suite, writes eval_report.md
```

Outputs:
- `out/shortlist.html` — the ranked comparison the couple actually reads
- `runs/<id>/audit_trail.jsonl` — every step, tool call, and error, timestamped
- `runs/<id>/drafts/*.txt` — drafted inquiry emails (for human review)
- `runs/<id>/report.json` — decisions + cost per venue
- `evals/eval_report.md` — pass rate and failure categories

### Real mode

```bash
cp .env.example .env      # add ANTHROPIC_API_KEY (search uses the same key)
export AGENT_MODE=real
python main.py --criteria criteria.json
```

Mock mode exists so the demo is deterministic and evals run free in CI. The only
difference is `src/llm.py` and `src/tools.py` swapping fixtures for live calls;
the agent, schemas, guardrails, and evals are identical in both modes.

## Frontend

A run produces two views in `out/`:

- **`dashboard.html`** — a four-quadrant "command center": an interactive 3D
  globe (top-left) with a marker per venue colored by decision, plus mission
  criteria, ranked recommendations, and escalations + cost telemetry. Open it in
  a browser (it pulls globe.gl from a CDN, so it needs internet the first load;
  the run data is inlined). Clicking a globe marker flies to it and highlights the
  matching venue card. Generated by `src/dashboard.py`.
- **`shortlist.html`** — a plain comparison table, generated by `src/report.py`.

To regenerate or restyle the dashboard in Claude Design, use
`claude_design_prompt.md`.

### Running the command center locally

```bash
pip install -r requirements.txt            # includes the optional server extras
python main.py --criteria criteria.json    # generate a dashboard first
uvicorn server:app --host localhost --port 8420
```

Then open **http://localhost:8420**. (`python server.py` does the same thing;
override with `CRITERIA_SERVER_HOST` / `CRITERIA_SERVER_PORT`.)

Port 8420 rather than 8000 only because 8000 is the port every other Python
project reaches for first. Any free port works — the server takes the port from
the command line and the browser-origin check keys on the *host*, not the port,
so nothing breaks when you move it.

`localhost` and `127.0.0.1` are the same loopback interface; use whichever URL
you prefer. Do not bind `0.0.0.0` — there is no auth, so that would publish your
criteria and a send button to your whole network.

| Endpoint | What it does |
|---|---|
| `GET /` | serves the existing dashboard, unchanged |
| `GET /report` | current run data, in the exact shape the page renders from |
| `GET /criteria` | current `criteria.json` + plottable regions + validator limits |
| `POST /criteria` | validates and saves criteria. **Does not run the agent.** |
| `POST /run` | runs the agent on the saved criteria, returns the fresh report |
| `GET /draft?url=` | the agent's draft for one venue, for a human to edit |
| `POST /send` | sends **one** venue's reviewed inquiry |
| `GET /auth/status` | whether Gmail is connected, and in which mode |

**Inlined data became fetched data.** The generated `out/dashboard.html` still
carries a snapshot of the run, but it is now a *seed*: served by the server, the
page fetches `/report` on load and replaces `DATA` with the fresh report after
every run, so edits and reruns show live. Both paths produce the identical
payload, because both come from `dashboard.build_data()`. Opened straight off
disk with no server, the page falls back to its inlined snapshot and renders
read-only — exactly as it always did.

**Edit / rerun flow.** *Edit criteria* → change fields → *Update criteria*
(validates server-side, writes `criteria.json`) → *Run agent* (runs the agent,
returns a new report, and re-renders all four quadrants from it).

**Send flow.** Three steps, one venue at a time:
1. A recommended card shows **Send inquiry** only if the extractor found an
   email on that venue's page. Otherwise it reads *"no email found — send
   manually"* and there is no button.
2. Clicking it loads the agent's draft, editable. The recipient is displayed
   but **not editable** — it comes from the venue record.
3. *Review & send* shows the final recipient, subject and body read-only.
   *Confirm send* posts to `/send`, which re-checks the recipient against the
   stored record and refuses any mismatch. The card is then marked
   **"inquiry sent"** with a timestamp.

Escalated venues (quadrant 04) are read-only and have no send control.

Already-sent venues are remembered in `sent_log.json` at the repo root, *outside*
`runs/`, so a rerun cannot resurrect the button and email a venue twice.

### Gmail setup (only needed to really send)

OAuth only, scope **`gmail.send`** and nothing else — it cannot read your mail.
No password is ever handled, typed, or stored by this system.

1. Google Cloud Console → enable the **Gmail API**
2. Create an **OAuth client ID** of type *Desktop app*, download the JSON
3. Save it as `credentials.json` in the repo root (git-ignored)
4. `python -m src.sending --authorize` — consent happens in your browser and
   writes `token.json` (git-ignored, mode 600)
5. `python -m src.sending` prints the current auth status

`credentials.json`, `token.json`, `.env` and `sent_log.json` are all covered by
`.gitignore`. `.env.example` (blank placeholders) is the committed template.

### Mock mode replays fixtures — it does not search

This is the single most confusing thing about the demo, so the dashboard now
says it out loud: a **`mock data`** badge sits in the header, and any region that
came back empty is listed under the telemetry with the reason.

In mock mode `search_venues()` reads `fixtures/search_results.json` and returns
only the venues written there. A region with no fixture returns **zero** results
— which is why searching six countries can evaluate three venues. That is the
fixture set being small, not the criteria being strict.

Fixtures currently exist for: 'Italy', 'Greece', and 'Portugal'.

### Going live

Real mode searches for real venues, reads their real pages, and (on an explicit
per-venue confirmation) sends real email. Three things to set up, in order.

**1. One API key.** Put it in `.env` yourself — the file is git-ignored, and no
key should ever be pasted into a chat, a commit, or a screenshot.

```bash
cp .env.example .env        # then edit: ANTHROPIC_API_KEY
```

Search needs **no second vendor**. `tools.search_venues()` calls the Claude
API's server-side `web_search` tool, billed to the same key. Google
Programmable Search was tried first and abandoned: new Cloud projects are no
longer granted Custom Search JSON API access (`403 PERMISSION_DENIED` on two
independent projects with the API enabled), and its "search the entire web"
setting is deprecated — which made it the wrong tool regardless, since this
agent exists to discover venue sites nobody listed in advance.

**Candidates come from the search result blocks, never from the model's prose.**
When the search tool hits `max_uses`, Claude helpfully finishes its written
answer with venues from memory — real-looking names, real-looking URLs, no
search behind them. Reading that text would inject invented venues at the very
top of the pipeline, upstream of every anti-hallucination guard. So
`_results_from()` reads only `web_search_tool_result` blocks and discards the
text.

**2. Search + extraction only** (no sending yet). Confirm the results look sane
before wiring up email:

```bash
export AGENT_MODE=real
python main.py --criteria criteria.json
```

**Nothing caps how many venues a run evaluates.** There is no dollar ceiling,
no per-region search limit, and no cap on candidates:

| Setting | Default | Meaning |
|---|---|---|
| `SEARCH_MAX_USES` | `0` | uncapped — the model searches until new angles stop surfacing new venues |
| `MAX_VENUES_PER_REGION` | `50` | venues evaluated per region, in search-relevance order (`0` = uncapped) |
| `MAX_STEPS` | grows per region | runaway-loop guard only; extended by the real venue count as each region is searched |

Search itself is uncapped; the venue cap is what bounds the run. `MAX_VENUES_PER_REGION`
used to be **8** and was the binding constraint — a live Italy search returned
**118** venues and all but 8 were discarded before anything looked at them.
Uncapped is the other extreme: 118 venues at ~26s each is ~50 minutes for one
region. **50** is the working default — broad enough that the shortlist is not
an artifact of the cap, bounded enough that three regions take about an hour.
Set `0` for no cap.

**Real runs are slow, and now slower by design.** Search alone was ~2.5 min per
region when capped at 3 searches; uncapped it runs longer, and every venue found
then needs a page fetch plus ~4 model calls. A four-country run can be ~100
venues. `/run` allows 2 hours (`RUN_TIMEOUT_SECONDS`) as a "did something wedge"
ceiling, and search retries twice rather than five times because each attempt is
minutes long and costs real money.

**Uncapped search must resume on `pause_turn`.** The server-side tool loop
pauses after ~10 iterations instead of ending. A caller that ignores that keeps
only the first batch — indistinguishable from "that is all search found" — so
`search_venues()` resumes up to `SEARCH_MAX_CONTINUATIONS` (6) times.

Cost scales with what is found: roughly **$0.20+/region** for search plus
**~$0.02/venue**. A wide four-country run is therefore a few dollars, not cents.

`.env` is read automatically — setting `AGENT_MODE=real` there is enough, no
`export` needed. An explicit environment variable still overrides the file,
which is how the eval suite and tests stay offline regardless of what `.env`
says.

**3. Gmail**, only when you actually want to send. OAuth, scope `gmail.send`
only — see the Gmail setup section above. Until a token exists, `/send` refuses
with a message telling you what is missing; it never fails silently or half-sends.

Sending rules do not change in real mode: one venue, one click, one confirmation
screen, recipient re-derived from the venue's own page, and a venue you have
already contacted cannot be contacted again.

**What real mode exercises that mock never did.** Live pages arrive as HTML, and
live models phrase their answers loosely. Both are handled — `tools.html_to_text`
strips markup to the text a human would read (before capping, so the cap does not
land inside `<head>`) and unescapes entities so quote-grounding still matches;
`_loads_lenient` in `agent.py` tolerates ```json fences and stray preamble
without ever repairing the JSON itself. Mock mode runs through the same HTML
conversion, so it stays evidence about real behavior rather than a friendlier
parallel universe.

### Mock mode is the default, and stays fully offline

With `AGENT_MODE=mock` (the default) the entire command center works with no
Gmail account, no credentials, and no network:

- `/run` runs the agent against fixtures
- `/send` does **not** touch Gmail. It writes the final text to
  `runs/<id>/drafts/<venue>.sent.txt` and marks the card *"inquiry sent (demo)"*

`tests/test_server.py` enforces that last point rather than trusting it: the
mock send runs with outbound DNS and connections blocked, and fails if anything
tries to reach off-box. Real delivery happens only in real mode with a valid
token.

### Tests

```bash
python -m evals.run_evals      # agent behavior + criteria intake (CI gate)
python -m tests.test_server    # server: criteria intake, send rules, mock send
```

The eval suite runs against `evals/eval_criteria.json`, pinned deliberately —
`criteria.json` is user-editable from the dashboard now, and editing a guest
count in a browser must not fail the agent's golden dataset.

**How criteria reach the agent.** Browser → `POST /criteria` →
`src/criteria_io.validate()` → atomic write to `criteria.json` (previous kept
as `criteria.json.bak`) → the next `Agent(criteria, ...)` reads that file. The
agent's own input path is unchanged; it still just reads `criteria.json`.

**What the validator enforces** (`src/criteria_io.py`, graded by the
`criteria intake` cases in the eval suite):

- `guest_count` a positive whole number, `budget_ceiling_usd` a positive
  number — `true`, `"85"`, `85.5`, `0` and negatives are all rejected (`bool`
  is an `int` subclass in Python, so it is rejected explicitly).
- `regions` non-empty, deduped, length- and count-capped, and each must resolve
  in `REGION_COORDS` — unknown regions are **rejected** with a message naming
  the bad one and listing what is available. Two granularities are supported and
  mix freely in one search:
  - **a country** — `Italy`, `Portugal` — for "somewhere in Portugal that fits",
    before you have a town in mind
  - **`City, Country`** — `Tulum, Mexico` — when you do

  Matching is case- and spacing-insensitive (`italy`, `TULUM, MEXICO` both
  resolve), and the canonical spelling is what gets stored, so `criteria.json`,
  the agent's search query, and the globe lookup always agree on one string.
  Country markers get a deliberately wide scatter on the globe: a venue found
  under "Italy" is somewhere in Italy and we do not know where, so a tight
  cluster on the centroid would imply precision we do not have. Adding a real
  geocoder is what removes this allowlist entirely.
- Free text (`vibe`, `must_haves`, `nice_to_haves`, `date_window`, `couple`) is
  length-capped and flattened to a single line with control characters removed.
  These strings are serialized into the SCORE and EMAIL prompts as JSON data,
  so they are a prompt-injection surface; flattening means an injected
  instruction block cannot be laid out as one, and the value never leaves a
  JSON string position. The layers that actually decide outcomes — grounding,
  must-have checks, the budget disqualifier — are code and never read it.
- A strict field whitelist. Unknown keys are an error, so the editor cannot
  become a way to introduce fields the agent never agreed to read.

**Security posture — read this before exposing it anywhere.** Locally the server
binds `localhost` and has **no authentication**; the socket is the entire
boundary. It additionally refuses cross-origin requests, which is what stops a
public web page from resolving a hostname to 127.0.0.1 and posting to it from
your browser. `POST /run` honors `AGENT_MODE`, so with `AGENT_MODE=real` in
`.env` a click on *Run agent* starts a real, billable run — keep it on `mock`
if that is not what you want.

### Deploying (read-only demo)

A public URL removes the socket boundary, and the three POST routes are exactly
the ones a stranger should not have: `/run` spends API credit for minutes at a
time, `/send` emails a real venue, `/criteria` rewrites the agent's input. So a
deployed instance runs **read-only**.

```bash
DEMO_READONLY=1 PORT=8080 python server.py
```

- Every `GET` works — dashboard, `/steps`, `/prompts`, `/report`. That is the demo.
- Every `POST` returns 403, enforced in middleware. The UI also drops the write
  controls, but that is cosmetic; the middleware is the control.
- **The server refuses to start** on a non-loopback bind unless `DEMO_READONLY`
  is set, so you cannot publish a run button by forgetting a flag.
- `demo/` is a committed snapshot of one real run (contact emails stripped) used
  only when `runs/` is empty, so a fresh container shows real results instead of
  an empty page. See `demo/README.md`.

`railway.json` and `Procfile` are checked in. On Railway: point it at the repo,
set **`DEMO_READONLY=1`**, and set no API key — the demo needs none. Railway
supplies `$PORT`.

**What a real multi-user version would add:** authentication and per-user
authorization, so runs and sends belong to someone; managed secrets rather than
files on a laptop; a geocoder so arbitrary regions resolve to coordinates
instead of a static `REGION_COORDS` lookup; and a job queue with run IDs,
cancellation and concurrency limits instead of the current single blocking
subprocess under a lock.

## How it works

```
criteria.json ─► [search] ─► [dedupe: seen this venue already?]
                                     │ new            └─► collapse (cross-region/domain)
                                     ▼
                             [classify: venue? cheap model]
                                     │ venue
                                     ▼
                              [fetch page] ─► [page usable?] ─► shell/error → escalate
                                     │                           (no extract call spent)
                                     ▼
                     [extract → VenueRecord]  ◄─ schema validation + 1 retry
                                     │                 (invalid → escalate)
                                     ▼
                     [ground vs page]  ◄─ quote must be ON the page, be about money,
                                     │     and be about a wedding; a capacity number
                                     │     must sit next to a guest word
                                     │     ungrounded → strip the claim → escalate
                                     ▼
                     [score vs criteria]  ◄─ budget disqualifier (deterministic)
                                     │     ◄─ must-haves re-checked in code
                                     │        unmet → reject · unconfirmed → escalate
                                     │     ◄─ confidence capped by page evidence
                                     │        below 0.80 → escalate
                          recommend  │  reject / escalate
                                     ▼
                      [draft email]  ── HUMAN GATE: written to disk, never sent
```

## Design decisions worth calling out

- **The anti-hallucination rule is the heart of it.** Destination venues rarely
  publish prices. The naive v1 prompt ("what's the price?") invented numbers. v2
  makes `request_only` a first-class answer and the schema (`schemas.py`) rejects
  any price without a verbatim source quote. The eval's `casa-jaguar` case guards
  this: correct behavior is "by request", not a made-up figure.
- **A price in the wrong currency is a wrong price.** `price_low_usd` has no
  currency field, so a Tuscan venue quoting "28,000 EUR" or a Tulum one quoting
  "45,000 MXN" cannot be recorded as-is — 45,000 MXN is about $2,400, and the
  budget disqualifier would compare it to a USD ceiling and reach a confident
  wrong answer. Non-USD prices are stripped to `request_only` and escalated for
  a human to convert. Searching Europe made this the common case rather than an
  edge case; the `borgo-antico` eval guards it.
- **A schema can only check a record against itself.** That leaves the harder
  half of hallucination untouched, so `grounding.py` checks the record against
  the page it came from. It catches two things the schema cannot: a quote that
  is fluent and plausible but appears nowhere on the page, and — the subtle one
  — a quote that is real, verbatim, and about the wrong thing. Venue pages are
  full of numbers that are not wedding numbers: `48 casitas`, `founded in 1918`,
  `3,500 square feet`, `$450 per night`. A number is only a price if its quote
  talks about money *and* about a wedding; a number is only a capacity if it
  sits next to a guest word. Ungrounded claims are stripped back to
  `unknown`/`request_only` and the venue escalates — because an extractor caught
  overclaiming is not trusted on the rest of the record.
- **The model proposes; code decides.** Must-haves are re-checked field by field
  in `scoring.py`, where "the page said no" (reject) and "the page never said"
  (escalate) are kept strictly apart — a null field never counts as a pass. The
  model's confidence is treated as a ceiling that evidence can lower and nothing
  can raise, which is what makes the 0.80 escalation threshold mean something.
  Both land in the rationale, so the shortlist shows which field confirmed which
  must-have and why the confidence moved.
- **A 200 OK is not a page.** Venues live on JS site builders, so the common
  failure is a live URL returning an app shell. Extracting from it yields an
  all-null record that reads like "the page was silent" — quietly laundering a
  fetch failure into an incomplete-information verdict. `tools.page_problem`
  catches it before the extraction call is spent.
- **Cheap model for the cheap job.** Classification (venue vs listicle) runs on
  Haiku; extraction and scoring run on Sonnet. Cost is metered per venue.
- **Deliberate memory, not a database.** A flat `seen` map plus an identity
  index is enough; nothing needs to outlive the run, so there's no vector store.
  The identity index exists because search does not respect the regions we
  search by: the same venue returns under two regions and two domains, and
  without collapsing it the couple sees it twice and it may be drafted two
  different emails. Name matching there is deliberately conservative — a false
  merge silently deletes a real candidate, which is worse than a visible
  duplicate.
- **Multi-agent was considered and rejected.** The task is a linear per-venue
  pipeline; decomposing it into planner/executor/synthesizer agents would add
  coordination cost with no benefit. Knowing when *not* to reach for complexity
  is part of the judgment.
